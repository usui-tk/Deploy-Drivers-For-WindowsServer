# AMD Graphics Driver Research Toolkit 0.7.1 — Windows Build OOM Review and Hardening

Date: 2026-08-11  
Source evidence: `AmdGraphicsDriverResearchEvidence_20260811-034850_Windows.zip`

## Executive summary

The Windows PowerShell 5.1 rerun demonstrates that the **0.7.0 product-driven front end and deep-analysis engine worked through Inspect**. The run selected 23 unique AMD installer artifacts (estimated 19.54 GiB), downloaded all 23, extracted all 23 to INF-bearing payloads, and inspected **482 INF files with zero parse failures**. The only failing stage was Build.

Build failed with `System.OutOfMemoryException` inside `ConvertTo-Json`. This was not an AMD-site/download/extraction/INF-parser defect. It was a scalability defect in the 0.7.0 intermediate-data model: Inspect serialized every driver record for every artifact into one monolithic `inventory/driver-packages.json`, and Build then deserialized and embedded that dense object before serializing another large JSON object.

The Evidence snapshot makes the defect concrete: the uncompressed `snapshot/inventory/driver-packages.json` member is **956,685,128 bytes (~913 MiB)**. Its ZIP-compressed size is only ~17 MiB because the JSON contains extensive repeated/pretty-printed structure; however PowerShell must materialize the uncompressed object/string in memory. `ConvertTo-Json` ultimately failed while building the output `StringBuilder`.

Version **0.7.1** fixes this architecturally rather than adding a memory threshold.

## Root cause

0.7.0 used a single global driver list in Inspect and emitted all dense driver facts into one JSON envelope. Those records contain INF topology, identifiers, WDF evidence, and Windows Server analysis. Windows Server analysis can itself contain selected Models/HWID evidence for four Server profiles. This is valid canonical evidence, but it is not a safe **cross-artifact intermediate storage unit**.

Build then read this monolithic JSON as one PowerShell object, embedded dense records into the top-level inventory/canonical generation path, and called `ConvertTo-Json`. Windows PowerShell 5.1 therefore needed enough memory for the large input text, the expanded PowerShell object graph, and the new JSON `StringBuilder` at the same time.

This is why the failure appeared only after the new curated product-group workflow successfully expanded the run to 23 artifacts. Small five-artifact qualifications did not exercise the same scale.

## 0.7.1 storage and Build changes

### Inspect memory boundary

`inventory/driver-packages.json` is now a lightweight index using:

```text
amd-graphics-driver-packages-index/3.0
```

Dense driver records are stored **one ArtifactKey per file**:

```text
inventory/driver-packages-artifacts/<release>/<artifact>.json
```

using:

```text
amd-graphics-driver-packages-artifact/1.0
```

The index stores artifact identity, counts, parse-failure count, WDF declaration counts, and a relative `DetailJson` pointer.

### Build memory boundary

Build:

1. reads one artifact detail JSON;
2. creates that artifact's canonical JSON;
3. updates lightweight aggregate indexes/INF×Server summary rows;
4. releases the dense object;
5. forces an artifact-boundary garbage collection;
6. proceeds to the next artifact.

The top-level research inventory no longer embeds every driver package.

### Aggregate views

- `inf-topology.json` is an artifact/canonical index rather than another duplicate of all topology.
- aggregate Windows Server JSON stores selected-HWID **counts**, not duplicate selected-HWID arrays.
- the default `device-server-compatibility-matrix.csv` is an INF × Server summary.
- full per-HWID cross-artifact CSV expansion is opt-in via `-EmitDetailedDeviceMatrix` and is written separately.
- historical aggregates are preserved from compatible lightweight aggregate indexes/rows; Build does not reparse every dense historical canonical JSON on each normal run.

### JSON serialization

New generated JSON uses compact serialization. A replay transformation of the same 482-INF Windows Inspect evidence produced 23 per-artifact compact detail files totaling about **181 MB**, with the largest individual detail file under **18 MB**, instead of one ~913 MiB pretty-printed cross-artifact JSON file.

### Migration and stale-data handling

Build explicitly rejects legacy monolithic `driver-packages.json` and asks the operator to rerun Inspect under 0.7.1. A new Inspect clears `inventory/driver-packages-artifacts/` before writing current-run details. Acquire/run cleanup also removes this run-scoped detail directory while preserving canonical `inventory/releases/**` history.

The final run assessment was also updated so the new index schema is evaluated correctly; it reports indexed INF count and parse failures rather than looking for the removed top-level `DriverPackages` property.

## Regression results

### Full 23-artifact Build replay

The Windows Inspect evidence was partitioned by ArtifactKey into the new per-artifact storage envelopes and replayed through the final 0.7.1 Build implementation.

Result:

```text
Build: PASS
Artifact records: 23
INF rows: 482
INF × Server rows: 1,928
Detailed per-HWID aggregate rows: 0 (default; opt-in only)
Elapsed: 25.78 s (stage) / ~28 s process wall time
Peak RSS: 856,952 KiB under PowerShell 7.6.4
```

This directly exercises the same 23-artifact / 482-INF dataset that caused the Windows 0.7.0 Build OOM.

### Real-artifact regression

The real AMD PRO Edition 26.Q1 Windows Server 2022 Vega/Polaris artifact was re-run using the new Inspect and Build storage format:

```text
Test    PASS
Acquire PASS
Extract PASS
Inspect PASS — 5 INF, parse failures 0
Build   PASS — 20 INF×Server rows
Final assessment: Pass
```

This confirms that the new per-artifact Inspect output is produced by the actual parser path, not only by the replay converter.

## Acceptance status

The defect is considered **fixed at design/implementation level** and regression-tested on PowerShell 7.6.4 using both the full Windows Evidence dataset and a real AMD artifact.

The remaining confirmation gate is a Windows PowerShell 5.1 rerun with 0.7.1. The expected behavior is that Inspect emits a small index plus per-artifact detail files and Build completes without materializing one cross-artifact 900+ MiB JSON object.

Historical 0.7.0 Evidence remains unchanged.
