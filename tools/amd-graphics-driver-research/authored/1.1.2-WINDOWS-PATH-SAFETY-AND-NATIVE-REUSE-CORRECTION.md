# Graphics 1.1.2 Windows Path-Safety and Native-Reuse Correction

## Evidence basis

The retained Windows 11 / Windows PowerShell 5.1 run started at
`2026-08-17 15:15:05` and ran for `12:18:48`. Test through Inspect passed.
Signature static analysis completed for 1,545 unique files with 169
certificates, zero unexpected parse failures and zero signed-content digest
mismatches.

Native verification then produced 2,643 SignTool `File not found` results. Every
failed target path was at least 260 characters (observed range 260–357). The
files existed and PowerShell Authenticode could read them. The defect boundary
was therefore the native SignTool path contract, not AMD package/catalog bytes.

## Implemented correction

1. `PathSafety` is automatically inserted before every run and has no bypass.
2. Windows qualification uses a 100-character tool-root maximum, a
   240-character full-path maximum and a 120-character vendor-relative reserve.
3. UNC and reparse-point qualification roots and configured output roots outside
   the tool folder are blocked. `LongPathsEnabled` is diagnostic only.
4. Real file probes cover lengths 200, 220 and 240. 7-Zip is tested at a
   220-character archive path. Required SignTool is tested against a copied,
   SHA-256-identical short alias.
5. Future downloads use `private/a`; extraction uses `work/x/aNNNN/cNNNN`;
   native verification uses `work/n/fNNNNNN.ext`; Evidence uses `private/r`.
6. 7-Zip `l -slt` output is evaluated after Acquire and before Extract, with a
   second check before each nested container extraction.
7. Original filenames, URLs, installer SHA-256 values, product groups and
   selection tracks are retained in mapping and inventory evidence.
8. Every Windows-native Authenticode, catalog API and SignTool operation uses a
   SHA-256-verified byte-identical short alias.
9. `SignatureNative` validates the existing plan, installer set, complete file
   SHA-256 set, static schema and zero-error summary, then reuses static evidence
   and reruns only native checks.

## Qualification boundary

The correction does not claim Windows qualification from local/Linux tests.
The next user run is purpose-specific and SHALL reuse the existing tool-local
`inventory`, `private` and `work` folders. It SHALL NOT repeat product discovery,
AMD download, extraction, INF inspection or static CMS analysis.

Windows Server remains separately unauthorized until Client correction evidence
is reviewed and explicitly accepted.
