## 3. 0.7.0 design decision

The no-switch default no longer requires AMD sitemap enumeration of support-product pages.

Instead it uses a **versioned curated product-group research catalog** in `data/seed-products.json`:

```text
CatalogKind     = CuratedProductGroups
CatalogVersion  = 2026-08-11.1
CoveragePolicy  = RepresentativeProductPerProductGroup
```

Each row is one AMD official support product page used as the representative entry point for one declared product group. The catalog is deliberately **not** a claim to enumerate every AMD product model.

## 4. Selection semantics remain dynamic

The catalog only defines **which product groups to research**. Driver versions are not hard-coded.

For every product group, ProductMetadata parses the current support page and Previous Drivers page. Select then uses:

```text
SelectionTrackKey = ProductGroupKey | OperatingSystemTrack | PackageFamily
```

and selects the newest release from each of the newest three available **driver major generations**. ArtifactRole remains evidence but does not fragment historical generations. Identical direct AMD EXE URLs are globally deduplicated.

Thus the policy remains:

```text
product group catalog = versioned / curated
release versions      = dynamically read from AMD product pages
3-generation choice   = dynamically computed
EXE acquisition       = globally deduplicated
```

## 5. New metadata-coverage hardening

A curated catalog is only useful if every declared representative can actually be evaluated.

0.7.0 therefore upgrades product-driver mapping to `amd-graphics-product-driver-mapping/1.1` and emits:

```text
MetadataCompleteness
CanProceedToAcquire
LatestFetchFailureCount
PreviousFetchFailureCount
NoDriverEntryProductCount
FetchFailureProductKeys[]
NoDriverEntryProductKeys[]
```

Default Acquire is blocked if MetadataCompleteness is not `Complete`.

This prevents a temporary AMD page failure or a missing Previous Drivers page from silently reducing a three-generation baseline to one or two generations.

## 8. Important scope statement

0.7.0 solves the observed practical problem by using an explicit product-group research scope instead of pretending the AMD sitemap is a complete product catalog.

It does **not** claim:

- every AMD product model is represented;
- every legacy family is in default scope;
- a representative product page proves every model in the product group maps identically;
- static INF candidacy proves Windows Server runtime compatibility.

Those boundaries remain explicit evidence/analysis constraints.


## Package integration note

This 0.7.0 package uses the curated product-group design described above. The historical 0.6.1/0.6.2 `SeedOnlyFallback` behavior remains supported only for legacy/custom seed catalogs; it is no longer the default normal research scope. The current catalog is versioned separately and deliberately does not claim every AMD product model.
